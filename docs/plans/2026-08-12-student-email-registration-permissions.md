# 学生邮箱注册与权限体系设计总结

日期：2026-08-12
执行者：Codex

## 1. 目标

允许符合条件的学生使用学校邮箱自行注册账号，但学生账号默认只能作为买家使用：

- 可以购买 API 额度。
- 可以查看和处理自己的订单。
- 可以使用订单售后、纠纷、评价等买家功能。
- 不可以参与拼车。
- 不可以发布拼车。
- 不可以发布或销售 API 额度。
- 不可以管理 API 探针及商家工作台。

所有限制必须由后端权限校验。前端菜单隐藏只负责改善使用体验，不能作为唯一限制。

## 2. 学生注册管理

新增管理员页面：

```text
/admin/student-registration
```

页面名称为“学生注册管理”，包含注册总开关和院校邮箱域名白名单。

### 2.1 注册总开关

管理员可以控制是否开放学生邮箱注册。

关闭后：

- 不再发送新的注册验证码。
- 不允许确认新的学生注册。
- 已注册学生账号不受影响。
- 已有订单及售后功能继续正常使用。

### 2.2 院校邮箱域名白名单

管理员维护允许注册的学校邮箱域名，例如：

```text
student.example.edu.cn
mail.example.edu
```

每条配置包含：

```text
院校名称
精确邮箱域名
启用状态
创建人
修改人
操作原因
版本号
创建时间
修改时间
```

域名规则：

- 使用精确域名匹配。
- 不因为邮箱是 `.edu` 或 `.edu.cn` 就自动放行。
- 不支持 `*.example.edu.cn` 之类的通配符。
- 发送验证码和确认注册时都要检查域名是否启用。
- 停用域名只阻止新注册，不取消已有学生账号的权限。
- 新增、修改、启用和停用都需要管理员权限并记录操作日志。

## 3. 学生邮箱永久身份记录

学生首次完成注册时，需要创建独立的永久身份记录：

```text
student_email_claims
```

记录内容包括：

```text
user_id
normalized_email
institution_domain_id
claimed_at
```

它和用户可修改的资料邮箱是两个概念：

- `users.email`：当前资料或联系方式邮箱，可以修改。
- `student_email_claims.normalized_email`：首次建立学生身份的学校邮箱，不可修改、删除、释放或转移。

该设计用于防止以下重复注册漏洞：

```text
注册学生账号
→ 修改账号邮箱
→ 原学校邮箱被释放
→ 再用原学校邮箱注册新账号
→ 无限创建学生账号
```

数据库必须保证：

- 一个学生邮箱终身只能创建一个账号。
- 同一邮箱的并发注册最多成功一次。
- 修改资料邮箱不会释放学生邮箱。
- 封禁、停用账号也不会释放学生邮箱。
- 管理员不能直接把学生邮箱转移给其他账号。
- 如果邮箱已经注册，引导用户登录或找回原账号。

## 4. 注册流程

### 4.1 申请验证码

```http
POST /api/v1/auth/email-registration/start
```

请求示例：

```json
{
  "email": "user@student.example.edu.cn",
  "turnstileToken": "..."
}
```

后端依次检查：

1. Turnstile 验证是否通过。
2. 学生注册总开关是否开启。
3. 邮箱格式是否正确。
4. 邮箱域名是否在启用白名单中。
5. 学生邮箱是否已经被永久认领。
6. IP、用户和目标邮箱是否超过限流。
7. 发送注册验证码。

### 4.2 确认注册

```http
POST /api/v1/auth/email-registration/confirm
```

请求示例：

```json
{
  "email": "user@student.example.edu.cn",
  "code": "123456",
  "username": "campus_user",
  "password": "用户设置的密码"
}
```

确认时需要重新检查：

- 验证码正确且未过期。
- 院校域名仍然启用。
- 学生邮箱仍未被其他账号认领。
- 用户名是 3～24 位小写字母、数字、下划线或连字符，不在保留词中且全局唯一。
- 密码符合现有密码强度要求。

用户名不会被自动转小写、替换空格或生成备用名称；格式不合规返回 `USERNAME_INVALID`，保留词或占用冲突返回 `USERNAME_UNAVAILABLE`。用户名冲突时不会消耗仍然有效的验证码，用户可以换一个用户名重试。

以下操作必须在同一个数据库事务内完成：

```text
创建用户
→ 永久认领学生邮箱
→ 保存 Argon2id 密码凭据
→ 分配学生买家身份
→ 记录注册来源
→ 消费验证码
→ 创建登录会话
→ 写入安全的身份审计事件
```

任何一步失败，整个注册都回滚，不能产生半注册账号。

## 5. 登录

学生账号注册成功后，可以通过以下任一方式登录：

```text
用户名 + 密码
学校邮箱 + 密码
```

邮箱登录必须查询永久的学生邮箱记录，不能依赖可修改的资料邮箱。

密码找回不在本次实现范围内。未来新增找回流程时，必须复用同一套 purpose 隔离、HMAC 验证码和 Turnstile 约束，不能复用学生注册验证码。

## 6. 权限模型

使用明确的 capability，不再通过“有没有商家数据”或“有没有 linux.do 绑定”零散推断权限。

### 6.1 权限矩阵

| Capability | linux.do 用户 | 学生账号 |
| --- | ---: | ---: |
| `api_order.create` | ✅ | ✅ |
| `carpool.apply` | ✅ | ❌ |
| `carpool.publish` | ✅ | ❌ |
| `api_service.publish` | ✅ | ❌ |
| `api_quota.publish` | ✅ | ❌ |
| `api_probe.manage` | ✅ | ❌ |
| `admin.access` | 单独授权 | ❌ |

不创建 `api_order.after_sales` 或 `api_model_tester.use_owned_order` 这类全局 capability。订单售后、纠纷、评价、联系方式读取和已购订单模型测试，完全按照具体订单的参与方、资源归属、订单状态、时限和既有资格规则授权。

### 6.2 学生账号可以执行的操作

- 浏览市场。
- 购买 API 额度。
- 支付和查看自己的订单。
- 查看交付凭证。
- 确认凭证是否可用。
- 发起订单纠纷。
- 联系对应订单商家。
- 提交评价。
- 使用自己已购买订单支持的模型测试功能。

### 6.3 学生账号禁止执行的操作

- 申请加入拼车。
- 发布拼车。
- 发布 API 服务。
- 发布或销售 API 额度。
- 创建、修改、验证或删除探针连接。
- 访问商家订单管理和经营工作台。
- 获得管理员权限。

禁止操作统一返回：

```text
HTTP 403
code: CAPABILITY_REQUIRED
```

后端必须在数据库写入或外部请求之前完成权限检查。

## 7. 探针菜单逻辑

探针菜单不能再根据是否已经有探针、服务或商家订单决定是否显示。

正确逻辑：

```text
拥有 api_probe.manage
→ 始终显示“探针连接”
→ 即使当前探针数量为 0
→ 页面显示首次创建引导
```

学生账号没有 `api_probe.manage`：

```text
不显示探针菜单
直接访问路由也会被后端拒绝
```

这样可以解决新卖家因为尚未创建任何资源，反而看不到探针入口的问题。

## 8. 绑定 linux.do 后的升级

学生账号以后可以绑定 linux.do，并在原账号上完成升级。

升级后：

- 用户 ID 不变。
- 学生邮箱永久认领记录继续保留。
- 历史订单、纠纷、评价和记录全部保留。
- 能力从学生买家升级为普通 linux.do 用户能力。
- 获得拼车、售卖和探针管理权限。

绑定开始前必须在当前会话中重新验证密码；OAuth state 绑定当前用户、当前会话和 `link_linuxdo` purpose。成功绑定后轮换当前 Session 与 CSRF，其他已有会话会在下一次请求时根据新的持久身份事实重新投影能力。V1 不允许解绑。

如果该 linux.do 身份已经属于另一个账号：

```text
返回 OAUTH_IDENTITY_CONFLICT
不移动身份
不合并账号
不修改任何一个账号
```

V1 不提供自动合并或管理员强制合并。

## 9. 操作日志

需要记录以下成功操作：

- 学生账号创建及身份分配。
- 学生账号绑定 linux.do 后的能力升级。
- 院校域名新增、修改、启用和停用。
- 注册总开关修改。
- 管理员权限的真实授予或撤销。

普通业务能力由学生邮箱认领、linux.do 绑定和管理员权限这些持久事实确定，不提供任意 `capability.granted` / `capability.revoked` 管理接口，也不伪造这类操作日志。

日志中不能包含：

- 学生邮箱原文。
- 验证码。
- 密码或密码哈希。
- Turnstile token。
- Session 或 CSRF token。
- 联系方式。
- 请求体。

注册失败、Turnstile 失败、密码错误和权限拒绝只进入脱敏运行日志及聚合指标，不写入永久业务操作日志。

## 10. 当前实现状态

### 10.1 当前分支已经完成

- 密码登录与学生注册申请的 Cloudflare Turnstile 校验、一次性 token 重置、action/hostname 精确校验及 CSP。
- 默认关闭的学生注册总开关，以及院校域名的新增、改名、启停和乐观并发管理页面。
- 学生邮箱永久认领、资料邮箱隔离和数据库级跨账号占用保护；修改资料邮箱不会释放注册邮箱。
- 六位、十五分钟、最多五次尝试、重发作废且按 purpose 隔离的 HMAC 验证码。
- 学生邮箱注册、邮箱或用户名密码登录，以及注册事务内的用户、身份、密码、来源、会话和安全事件写入。
- 七项 canonical capability 的后端确定性投影、服务层校验、路由/menu/query 守卫和 OpenAPI/前端类型同步。
- 学生保留购买、订单售后、纠纷、评价和已购订单模型测试；拼车、售卖、探针与商家工作台被拒绝。
- 探针菜单改为只依赖 `api_probe.manage`，符合条件的新用户即使没有任何探针或服务也能看见入口。
- 学生账号经近期密码验证后原地绑定 linux.do；冲突不合并，成功后轮换 Session/CSRF，V1 不允许解绑。
- 联系方式真实 `usageScopes` 持久化；学生只能创建 `buyer` / `dispute` 用途，卖家用途在幂等开始和业务写入前被后端拒绝。
- 管理员统一操作日志页面、数据库筛选、混合来源复合游标、安全 action registry，以及探针操作专属追加式账本。

原 Turnstile 实现提交及迁入当前分支后的提交：

```text
f8ae8b3 feat(auth): integrate Cloudflare Turnstile
e92d21e feat(auth): integrate Cloudflare Turnstile
```

### 10.2 激活前检查

- 保持学生注册总开关关闭，直到目标环境配置至少一个真实院校域名并完成迁移、邮件发送和 Turnstile 冒烟测试。
- 使用隔离 PostgreSQL 完成从空库到当前版本的全链迁移、并发认领、审计游标和幂等故障注入验证。
- 完成前后端全量测试、类型检查、生产构建及真实浏览器桌面/移动端验收。

密码找回仍是后续独立任务，不属于本次实现。

## 11. 上线顺序

1. 部署数据库迁移与后端，保持学生注册总开关关闭。
2. 部署 OpenAPI 对齐后的前端和管理员配置页面。
3. 管理员录入并复核精确院校域名。
4. 在 staging 完成验证码、重复认领、学生权限、linux.do 绑定和审计日志冒烟测试。
5. 确认邮件发送、Turnstile、限流与监控正常后，再由管理员显式开启学生注册。
